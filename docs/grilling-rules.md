# grilling の運用ルール

grilling を回すときにだけ読むルール。CLAUDE.md の「# 仕様策定・要件定義」節が
最初のラウンドの前にこのファイルを Read するよう指示し、
`hooks/remind-grilling.sh` がプロンプトに「仕様」「要件」「spec」「requirements」を見つけたときに
同じことを思い出させる。

grilling スキル本体は `npx skills add`（mattpocock/skills）で入れた上流管理の
ファイルなので編集しない。以下はスキルの外側でこちらが守る運用ルール。
スキル現行版（2026-08 時点）の「frontier が空になったら終了」という文面に
接続しているので、スキルを更新したら終了条件の書き方を再確認する。

## 回す深さ

frontier が空になる（下の棚卸しを通す）まで質問し、暗黙の前提を残さない。
「軽くでいい」と言われたら省略してよいが、それはそう言われた作業にだけ効く。
後続の増分には持ち越さない。

## 増分での再発火

判定の3条件は CLAUDE.md に置いてある。ここには判定の補足を置く。

- 迷ったら回す。
- 「初回で枠は固まったから、以降は枠内の増分」は、当たらない理由にならない。
- ADR に値する選択かどうかは、ADR を実際に書くかどうかで決めない。書くかどうかは
  結果であって、判定の入力にしない。
- 既存の決定を覆す・定義を変える増分は局所的な修正に見えるが、定義を変えると
  その定義に依存する目標・判定・受け入れ基準がすべて無効になりうるので、必ず
  再発火の対象にする。まず変更する定義・決定を参照している箇所を洗い出し、
  それを frontier に載せる。

再発火した grilling は初回のやり直しではない。frontier は増分そのものと
洗い出した依存先に張ればよく、数問で空になるならそれで正しく終わってよい。
終了前の棚卸しも増分が触る枝に限ってよいが、「触る枝」と「触らないと判断した
枝」の列挙自体は省略しない。

## 選択肢を出す前に事実を確定させる

grilling を回すときは常に（仕様策定に限らない）、最初のラウンドを出す前に
事実確認と分析を済ませる。当たる順序は
公式ドキュメント → インストール済みスキル → 手元のリソース（lock・manifest・
実コード）。スキルは公式情報のキャッシュなので、スキルが自分を先に読めと言って
いればそれに従い、そのうえで一次情報で古びていないか確認する。記憶で書かない。

選択肢には根拠（出典・ファイル・バージョン）を必ず添える。根拠を書けない選択肢は
出さない。調べれば分かることを調べずに選択肢に混ぜない。調べる範囲は選択肢と
その根拠を書けるところまでで、書けたら止める。事実が取れなかった枝は「未確認」と
明示したうえで選択肢を出し、いつ・何を見て確定するかを添える。事実待ちで
ラウンド全体を止めない。

事実集めの分担は、手元の読み取り・検索がメインスレッド、Web を跨ぐ調査と広い
コードベース探索はサブエージェント。

## 終了前の棚卸し

「frontier が空」は自己申告で、思いついた枝を全部訪問した
以上のことを保証しない。空だと宣言する前に、訪問した枝・意図的に対象外にした
枝・未確定のまま持ち越す枝を列挙してユーザーに見せ、確認を取る。どの列にも
入らない枝が穴で、穴が出たら報告して終わりではなく frontier に戻してラウンドを
回す。システム設計なら、最低限この枝リストと突き合わせる:

- 目的・利用者・成功条件
- 機能スコープと非スコープ
- データ（何を入れ、何を入れないか）
- 認証・認可
- 提供面（UI・API・連携先）と UX
- 非機能（性能・コスト・上限）
- 運用（デプロイ・監視・失敗検知・定期実行・依存更新）
- セキュリティ
- 評価・受け入れ基準
- 段階計画
- 撤退・再検討の条件

これは埋めるための様式ではなく、自分で列挙した後に突き合わせる照合材料。
対象外の理由は「対象外にすると何を諦めるか」まで書く。「今回は不要」だけでは
理由にならない。持ち越す枝には、いつ・何を見て確定するかを添える。持ち越して
よいのは、いま調べても答えが出ないものだけ。調べれば分かるものを持ち越さない。

## 数値目標には裏取りをセットにする

「目標◯件」「◯割以上」は、狙い（決定）と
実データで達成可能か（事実）の合成で、事実を調べるのはこちらの仕事。目標が
確定する前に母集団を確認するか、まだ確認できないなら棚卸しの「持ち越す」列に
載せて確認手段を添える。「先に数値を決めて、後でデータを見る」を通さない。
